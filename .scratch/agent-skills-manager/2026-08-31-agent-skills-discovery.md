Other notable native `.agents/skills` readers (secondary confirmation): Gemini CLI (`~/.gemini/skills` **or `~/.agents/skills` alias**; workspace likewise), GitHub Copilot / VS Code (`.github/skills`, `.claude/skills`, `.agents/skills`; personal `~/.copilot/skills`, `~/.claude/skills`, `~/.agents/skills`), Android Studio (`.agents/skills` or `.android-studio/skills` at project root **or home dir**). agentskills.io's own integration guide recommends scanning `.agents/skills/` as the cross-client convention.

## Implication for a skill manager

You **cannot hide a "disabled" skill by leaving it in `~/.agents/skills`** — Codex, OpenCode, pi, Gemini CLI, and Copilot all read that directory directly. Disabling must be done via:

- **Codex**: `[[skills.config]]` in `~/.codex/config.toml` with `path = "…/SKILL.md"` **or** `name = "…"` and `enabled = false` (also `[skills] bundled`, `include_instructions`, `max_context_tokens`).
- **OpenCode**: `permission.skill` patterns (`allow`/`deny`/`ask`) in opencode.json, or `OPENCODE_DISABLE_EXTERNAL_SKILLS` / `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` env vars; `tools.skill: false` per agent.
- **Claude Code**: `skillOverrides` (`"off"` / `"user-invocable-only"`), `disable-model-invocation: true` in frontmatter, `disableBundledSkills` setting; or physically move the skill (Claude only reads `.claude/skills`, so moving it out of `.claude/skills` suffices for Claude).
- **pi**: `pi config` enable/disable (package-manager overrides), `--no-skills`, or remove from scanned dirs.

## Harness detail

### 1. Claude Code (Anthropic)

Sources: <https://code.claude.com/docs/en/skills> (accessed 2026-08-31); changelog `anthropics/claude-code` HEAD = v2.1.251 (accessed 2026-08-31).

- Locations (docs table): Enterprise = managed settings dir; Personal = `~/.claude/skills/<skill-name>/SKILL.md`; Project = `.claude/skills/<skill-name>/SKILL.md`; Plugin = `<plugin>/skills/<skill-name>/SKILL.md` (namespaced `/plugin-name:skill-name`).
- Project discovery: cwd + every parent up to repo root; skills in nested `.claude/skills/` _below_ cwd load lazily the first time Claude reads/edits a file in that subdir (qualified name `apps/web:deploy`); `--add-dir` dirs contribute their `.claude/skills/` too (requires `project` setting source); `/cd` (v2.1.246+) adds the new dir's skills. `permissions.additionalDirectories` setting does **not** load skills.
- Enterprise dir example given in docs: `/etc/claude-code/.claude/skills/<name>/` (Linux). Also claude.ai-synced skills downloaded to `~/.claude/skills/synced/` when `CLAUDE_CODE_SYNC_SKILLS=1` in non-interactive mode; folder name `synced` is reserved in all local locations. A skill folder with `.claude-plugin/plugin.json` loads as a plugin named `<name>@skills-dir`.
- **Symlinks**: "A `<skill-name>` entry in the enterprise, personal, or project skills locations can be a symlink to a directory elsewhere on disk. Claude Code follows the symlink and reads SKILL.md from the target directory, and if the same target is reachable from more than one location, Claude Code loads the skill once." Plugin skills handle symlinks differently (see plugins-reference "Share files within a marketplace with symlinks"). Changelog evidence of long-standing support: v2.0.62 "Fixed an issue where skill files inside symlinked skill directories could become circular symlinks"; v2.1.178 "Fixed Linux sandbox failing to start when `.claude/skills` or `.claude/hooks` is a symlink" (implies the skills dir itself may be symlinked, e.g. dotfiles/stow).
- **Timing**: loaded at session start (parents chain + add-dirs + personal/enterprise); file watchers pick up add/edit/remove under `~/.claude/skills/`, project `.claude/skills/`, and add-dir skill dirs within the session; a top-level skills dir created after startup needs a restart; bare mode doesn't watch. Loaded skill content stays in context for the session (not re-read per turn).
- **Collisions**: enterprise > personal > project; skill > `.claude/commands` file; any local skill overrides bundled skill (but not bundled aliases); plugin skills namespaced so no conflict; nested same-name skills coexist under directory-qualified names; synced skills are skipped when their name matches any other command (name comparison ignores case/spacing/lookalikes).
- Frontmatter: all fields optional; `description` recommended; command name = directory name for personal/project (frontmatter `name` is display only), frontmatter `name` used inside plugins. `description` + `when_to_use` truncated at 1,536 chars in the listing; `compatibility` ≤ 500 chars.

### 2. OpenAI Codex CLI

Sources: <https://developers.openai.com/codex/skills> (accessed 2026-08-31); source `openai/codex` main (post rust-v0.151.0, cloned 2026-08-31): `codex-rs/ext/skills/src/host_roots.rs`, `codex-rs/ext/skills/src/loader/host.rs`, `codex-rs/ext/skills/src/loader/discovery.rs`, `codex-rs/config/src/skills_config.rs`.

- Locations (docs): REPO = `.agents/skills` at cwd, at each ancestor between cwd and repo root, and at repo root; USER = `$HOME/.agents/skills`; ADMIN = `/etc/codex/skills`; SYSTEM = bundled (skill-creator, plan, etc.).
- Locations (code, superset of docs): Project config layer adds `<repo-root>/.codex/skills` (the `dot_codex_folder` of the Project layer, i.e. where `.codex/config.toml` lives; "loaded but disabled when untrusted"). User layer adds **`$CODEX_HOME/skills` — explicitly marked "Deprecated user skills location … kept for backward compatibility" — plus `$HOME/.agents/skills`**, plus system cache `$CODEX_HOME/skills/.system` (bundled skills installed there). Plugin skill roots and SDK `extra_skill_roots` are additional.
- **Symlinks**: docs — "Codex supports symlinked skill folders and follows the symlink target when scanning these locations." Code — `DirectorySymlinkPolicy::Follow` for scopes User/Repo/Admin; `DirectorySymlinkPolicy::Ignore` for the System cache. `HiddenDirectoryPolicy::Skip` — hidden (dot) directories pruned. Walk bounded: max depth 6, ≤ 2,000 dirs and ≤ 20,000 entries per root.
- Config (`~/.codex/config.toml`): `[[skills.config]]` entries with `path` (canonicalized SKILL.md path) **or** `name` selector + `enabled = bool`; later rules override earlier; path selectors stay effective even if no current skill matches. `[skills]` also supports `bundled.enabled`, `include_instructions`, `max_context_tokens` (default 2% of context, capped 10,000 tokens for the catalog). There is **no config option to add extra skill directories** — only enable/disable.
- **Timing**: "Codex detects skill changes automatically. If an update doesn't appear, restart Codex." (docs).
- **Collisions**: "If two skills share the same `name`, Codex doesn't merge them; both can appear in skill selectors." (`name_counts.rs` counts exact + lowercase-collapsed duplicates.)
- Frontmatter: docs — "The `SKILL.md` file must include `name` and `description`"; optional `agents/openai.yaml` for UI metadata, `policy.allow_implicit_invocation`, tool dependencies. Skills list includes each skill's file path; catalog budget ~2% of context / 8,000 chars, descriptions shortened first.

### 3. OpenCode (sst/opencode)

Sources: source snapshot of sst/opencode (read via a fork at commit `e23586af26`, dated 2026-08-14): `packages/opencode/src/skill/index.ts` (shipped discovery), `packages/core/src/skill.ts` + `packages/core/src/skill/discovery.ts` (v2 core), `packages/opencode/src/config/paths.ts`, `packages/core/src/util/glob.ts`, docs `packages/web/src/content/docs/skills.mdx`; live docs <https://opencode.ai/docs/skills>.

- Shipped discovery (`packages/opencode/src/skill/index.ts`), patterns: `EXTERNAL_SKILL_PATTERN = "skills/**/SKILL.md"` over `.claude` and `.agents` roots; `OPENCODE_SKILL_PATTERN = "{skill,skills}/**/SKILL.md"` over config dirs; `SKILL_PATTERN = "**/SKILL.md"` over explicit `skills.paths` and URL-pulled dirs.
  - Global: scan `~/.claude/skills` (unless `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS`/`OPENCODE_DISABLE_CLAUDE_CODE`) and `~/.agents/skills` (both unless `OPENCODE_DISABLE_EXTERNAL_SKILLS`).
  - Project: `fsys.up` from cwd to worktree finding `.claude` / `.agents` dirs; scan `skills/**/SKILL.md` in each.
  - Config dirs (each scanned for `{skill,skills}/**/SKILL.md`): `~/.config/opencode` (XDG; `OPENCODE_CONFIG_DIR` override), every `.opencode` dir from cwd up to worktree (unless `OPENCODE_DISABLE_PROJECT_CONFIG`), `.opencode` in `$HOME`, plus `OPENCODE_CONFIG_DIR`. So **both `skill` (singular) and `skills` (plural) are read** in current versions; docs emphasize plural.
  - Config option: `skills` key — v1 schema: array of paths or URLs ("Additional paths or URLs to discover skills from"); current schema: `skills: { paths: [...], urls: [...] }`. Paths: `~/` expanded, relative resolved against cwd; scanned as `**/SKILL.md`. URLs fetched into the cache (`~/.cache/opencode/skills/<hash>/`) from an `index.json` manifest (`.well-known`-style).
- **Symlinks**: every scan passes `symlink: true`, which maps to glob's `follow: true` — symlinked directories are traversed and symlinked files matched, so symlinked skill dirs (and symlinked parents) work. Dot-directories: `dot: true` for `.claude`/`.agents` scans; **not** set for `.opencode`/config-dir scans or explicit `skills.paths` (hidden dirs excluded there).
- **Timing**: discovered lazily once per project directory and cached in `InstanceState` for the life of the instance; no documented live reload (the v2 core loader even carries a TODO comment asking whether local skill sources should invalidate on fs-watch events). Restart / new session to pick up changes. _(Source-derived; docs are silent.)_
- **Collisions**: `state.skills[name]` is overwritten by later scans with a "duplicate skill name" warning → **last-scanned wins**. Scan order: built-in `customize-opencode` (registered first so any disk skill overrides it) → global external (`.claude`, then `.agents`) → project external (nearest ancestor first) → config dirs → `skills.paths` → `skills.urls`. Note this **inverts Claude Code's precedence** (in OpenCode, project/config-dir skills shadow global `.claude`/`.agents` skills of the same name). Docs simply advise: "Ensure skill names are unique across all locations."
- Frontmatter (shipped loader): requires `name` (string); `description` optional (listed only if present). The v2 core loader is more lenient (name falls back to file basename for top-level `*.md`). Docs say name+description required and describe spec-style name rules — docs are slightly stricter than the shipped parser. Permission system: `permission.skill` patterns with `allow`/`ask`/`deny` (deny = hidden from agent entirely).

### 4. pi (badlogic/pi-mono)

Sources: <https://github.com/earendil-works/pi> `main` (fetched 2026-08-31): `packages/coding-agent/docs/skills.md`, `packages/coding-agent/src/core/skills.ts`, `packages/core/...` (package-manager resource resolution), README.

- Locations (docs, confirmed in `package-manager.ts` / `skills.ts`):
  - Global: `~/.pi/agent/skills/` (root-level `*.md` files also discovered as individual skills) and `~/.agents/skills/` (root `*.md` ignored; nested `*.md` in grouping folders discovered if they declare skill frontmatter).
  - Project (only after project trust): `.pi/skills/` and `.agents/skills/` in cwd and **all ancestor directories up to the git repo root** (filesystem root when not in a repo) — `collectAncestorAgentsSkillDirs()`. Untrusted projects contribute no project skills.
  - Packages (`skills/` dirs or `pi.skills` in package manifest), settings `skills` array (files or dirs, `~/` expanded), CLI `--skill <path>` (repeatable, additive even with `--no-skills`).
  - Config dir override: `PI_CODING_AGENT_DIR` (default `~/.pi/agent`).
- Explicit cross-harness support doc: "To use skills from Claude Code or OpenAI Codex, add their directories to settings: `{"skills": ["~/.claude/skills", "~/.codex/skills"]}`".
- **Symlinks** (source `skills.ts`): each directory entry that is a symlink is resolved with `statSync` and followed if it points to a directory; a symlinked `SKILL.md` is followed if it points to a file; broken symlinks are skipped silently. Additionally, `loadSkills` canonicalizes every loaded skill path and **skips a skill whose realpath was already loaded** (so the same skill reachable through several symlinked locations loads once — first occurrence wins).
- Dot-dirs: skipped (`entry.name.startsWith(".")` → skip), as is `node_modules`. Recursion: a directory containing `SKILL.md` is a skill root (no further recursion into it); otherwise recursion continues into subdirectories.
- **Timing**: scans at startup (system prompt gets name/description catalog in XML per agentskills.io/integrate-skills; model loads full SKILL.md via `read` on demand). `/reload` reloads skills (and prompts/themes/extensions) mid-session. _(No automatic fs-watch hot-reload documented.)_
- **Collisions**: first-found wins (`Map.set` only when absent) with a `collision` diagnostic naming winner and loser paths. Combined with realpath dedup.
- Frontmatter (docs): implements the Agent Skills standard, "warning about most violations but remaining lenient". Required: `name` (≤64 chars, lowercase a-z/0-9/hyphens, no leading/trailing/consecutive hyphens — **pi deliberately does not require name == parent directory**, unlike the spec) and `description` (≤1024 chars, non-empty or skill not loaded). Optional: `license`, `compatibility` (≤500), `metadata`, `allowed-tools` (experimental), `disable-model-invocation` (hide from system prompt; `/skill:name` still works). Unknown fields ignored. Skills register as `/skill:name` commands.

### 5. The `~/.agents/skills` convention

- agentskills.io "How to add skills support to your agent" (<https://agentskills.io/integrate-skills>, accessed 2026-08-31): "Within each scope, consider scanning both a client-specific directory and the `.agents/skills/` convention … The `.agents/skills/` paths have emerged as a widely-adopted convention for cross-client skill sharing. While the Agent Skills specification does not mandate where skill directories live (it only defines what goes inside them), scanning `.agents/skills/` means skills installed by other compliant clients are automatically visible to yours, and vice versa." It also notes pragmatic scanning of `.claude/skills/` and recommends: project overrides user; warn on collisions.
- **Native readers confirmed from primary sources**: OpenAI Codex (USER scope + repo ancestor scan), OpenCode (global + project ancestors), pi (global + project ancestors, trust-gated), Gemini CLI (explicit "alias"), GitHub Copilot / VS Code (listed location), Android Studio (project root or home).
- **Not a native reader**: Claude Code (all docs discovery is `.claude/…`-rooted; no `.agents` support documented anywhere — absence-of-evidence, flagged).
- Installer ecosystems (secondary sources, for context): vercel-labs `skills` (`npx skills add`, skills.sh) treats a set of agents as "Universal" with project `.agents/skills/` (Amp, Kimi Code CLI, Replit, Universal — global `~/.config/agents/skills/` per its table) and maps per-agent dirs for the rest; companion managers (e.g. `tc9011/skills-manager`, Sentry `dotagents`) keep the source of truth in `~/.agents/` / `.agents/skills/` and **symlink into per-agent dirs** — which only works because those agents follow symlinked skill dirs.

## SKILL.md frontmatter spec (agentskills.io, <https://agentskills.io/specification>)

Directory = folder containing at minimum `SKILL.md`; optional conventions `scripts/`, `references/`, `assets/`.

| Field           | Required | Constraints                                                                                                                                                                                                                |
| --------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`          | Yes      | 1–64 chars; lowercase a-z/0-9 + hyphens only; no leading/trailing hyphen; no consecutive hyphens; **must match the parent directory name** (pi explicitly relaxes this; Claude Code uses dir name as command name instead) |
| `description`   | Yes      | 1–1024 chars, non-empty; what it does + when to use                                                                                                                                                                        |
| `license`       | No       | License name or reference to bundled file                                                                                                                                                                                  |
| `compatibility` | No       | 1–500 chars; environment requirements                                                                                                                                                                                      |
| `metadata`      | No       | String→string map                                                                                                                                                                                                          |
| `allowed-tools` | No       | Space-separated pre-approved tools (experimental; support varies)                                                                                                                                                          |

Progressive disclosure guidance: catalog (name+description) at startup ≈50–100 tokens/skill; SKILL.md body <5,000 tokens / <500 lines recommended; resources on demand.

Claude Code extends the spec (all optional): `when_to_use` (appended to description; combined cap 1,536 chars in listing), `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`/`disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `hooks`, `paths` (glob gating), `shell`, `metadata`. Spec-portable fields for upload/packaging: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Codex adds `agents/openai.yaml` sidecar (display name, icon, `policy.allow_implicit_invocation`, MCP tool dependencies). pi adds `disable-model-invocation` support and tolerates unknown fields.

## Uncertainties / caveats (explicit)

1. **Claude Code & `.agents/skills`**: treated as "not read" based on complete absence from official docs (skills, plugins-reference, settings). I did not find a statement that it will _never_ read it; behavior could differ in undocumented ways.
2. **Claude Code symlinked parent dirs**: docs explicitly cover symlinked _skill entries_; the changelog (2.1.178) implies the `.claude/skills` folder itself may be a symlink (sandbox startup fix), and third-party dotfile managers rely on it — but I did not find a doc sentence literally saying "parent dirs may be symlinks".
3. **OpenCode live reload**: "no live reload" is source-derived (per-instance cache, TODO comment about fs-watch); official docs are silent. Version drift is possible — my code snapshot is a fork of sst/opencode at 2026-08-14.
4. **OpenCode frontmatter strictness**: docs say `name`+`description` required; shipped parser requires only `name` (description optional). Docs also state a name-must-match-directory rule; a `NameMismatchError` type exists but is only exercised in tests, not enforced at discovery time.
5. **Codex `<repo>/.codex/skills`** is in code (Project config layer → `config_folder()/skills`) but absent from the docs table; trust-gating applies ("loaded but disabled when untrusted"). `$CODEX_HOME/skills` is documented as deprecated in code comments but still scanned; the official docs table omits it (third-party installers still target it).
6. **pi automatic hot-reload**: `/reload` is documented; I did not verify whether fs-watch auto-reload of skills happens without it.
7. Skill-manager ecosystem claims (skills.sh, skills-manager, dotagents) come from project READMEs, not the harness vendors.
