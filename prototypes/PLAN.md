# Prototype plan: three TUI stacks, one screen, fair comparison

## Purpose

Build the same minimal skillctl CLI + TUI three times so the choice between
stacks is based on feel and code shape, not spec sheets:

1. **Ink + TypeScript** (Node/tsx, Commander)
2. **OpenTUI + TypeScript** (Bun, Commander)
3. **Go + Bubble Tea v2** (Cobra)

Each prototype implements two surfaces: a dummy CLI (`skillctl <command>`, no
filesystem work, fixture data only) and the TUI screen with a filterable skill
list, staged toggling, and a simulated apply. No real filesystem mutation, no
config file, no locking. The goal is to answer four questions after using each
one:

- How does it feel while typing in the filter, scrolling, and staging?
- What does the CLI help and command ergonomics feel like (Commander vs Cobra)?
- What does the code look like, and which codebase would I want to maintain?
- What does cold start cost, and is it noticeable in practice?

## Ground rules for fairness

- **One shared UX spec.** All three implement the identical layout, keybindings,
  states, and colors defined below. No stack gets extra polish.
- **One shared fixture.** All three render the same 45-entry skill list from
  `prototypes/fixture/skills.json` (TS prototypes read it; the Go prototype
  embeds the same JSON at build time via `go:embed`). The fixture uses realistic
  names and descriptions, mixed enabled and disabled states, and a few skills
  that exist in two roots so the multi-root row renders in every prototype.
- **Simulated apply.** Enter shows a one-line change preview, applies after a
  300 ms spinner, flips state in memory, and shows a success message. No disk
  writes anywhere. This keeps the prototypes safe and makes the apply feel
  comparable.
- **No early feature creep.** If a stack makes something tempting (mouse
  support, animations), note it in the notes file instead of building it.

## Shared dummy CLI

Every prototype ships a `skillctl` binary backed by the same fixture and the
same shared UX data. All commands are read-only or simulated; nothing writes to
disk. The point is to feel the CLI-authoring ergonomics of Commander (both TS
prototypes) versus Cobra (Go), not to build real behavior.

Commands:

```text
skillctl                     no args prints help
skillctl list                print the fixture as a table (same glyphs as the TUI)
skillctl enable <skill>...   print "would enable <skill>" per name
skillctl disable <skill>...  print "would disable <skill>" per name
skillctl toggle <skill>...   print the resolved action per name based on fixture state
skillctl root list           print the fixture's root names and paths
skillctl doctor              print two or three canned findings from the fixture
skillctl tui                 launch the TUI (the actual prototype screen)
```

Shared behavior:

- `-h` / `--help` on every command, generated by the framework.
- Unknown command or unknown skill name: clear error, exit code 1.
- `list --json` prints the fixture as JSON on stdout; everything else prints
  human output.
- The TUI is never launched implicitly; only `skillctl tui` opens it.

Run it without installing by pointing each prototype's dev script at the CLI
entry point, for example `skillctl list` becomes
`pnpm --dir prototypes/ink exec tsx src/cli.ts list` and, for Go,
`go run . list` from the `go-tui` directory.

## Shared UX spec

### Layout

```text
 skillctl · 45 skills · 31 enabled · 14 disabled · 2 staged

 / implementation_

 ●  tdd                        red-green-refactor workflow…        universal
 ○  frontend-design            distinctive, intentional visual…    universal
 ●* impeccable                 audit and polish existing UIs       universal, codex

 space toggle   enter apply staged   / filter   r refresh   ? help   q quit
```

- Line 1, status bar: tool name, total count, enabled count, disabled count,
  staged count. Staged segment only appears when nonzero.
- Line 2: filter input, prefixed with `/`. Placeholder is dim. Esc clears it.
- Body: rows of `glyph name description roots`. Glyph `●` green for enabled,
  `○` dim for disabled. `*` after the glyph (yellow) marks a staged change.
  Description truncates with `…` at column width. Roots column truncates first.
- Selected row: inverted colors, full width.
- Last line: key hints, dim.

### Keybindings

| Key | Action |
| --- | --- |
| `j` / `k`, arrows | Move selection |
| `/` | Focus filter input |
| `esc` | Clear filter, or cancel apply preview |
| `space` | Stage/unstage toggle for selected row |
| `enter` | Apply staged changes: show preview line, spinner 300 ms, flip states, clear staged set |
| `r` | Refresh (reload fixture; brief flash of a spinner to feel the path) |
| `?` | Toggle help overlay listing all keybindings |
| `q` | Quit (ignored while filter input is focused and non-empty) |

Filter matches case-insensitively against name and description. Selection
stays on the same skill when filtering if it is still visible.

### Scenarios every prototype must handle visibly

1. Type `imp` in the filter and watch the list shrink in real time.
2. Stage three toggles, apply, watch the spinner and state flip.
3. Open the help overlay, close it.
4. `r` refresh mid-session.
5. Scroll a 45-row list with `j` held down (repeat rate), then with
   `--rows 500` to stress it.

Run commands:

```sh
pnpm --dir prototypes/ink install && pnpm --dir prototypes/ink dev
pnpm --dir prototypes/ink cli -- list            # dummy CLI
```

### Common flags

Every prototype accepts:

- `--rows N` stress fixture: duplicate fixture rows with suffixed names up to N
  entries (default 45).
- `--bench` print `startup→first frame` milliseconds to stderr after the first
  render, then exit. Measure each with `hyperfine` or at minimum five `time`
  runs, warm cache.

## Prototype A: Ink + TypeScript

**Stack:** Ink 5, React 18, ink-text-input, ink-spinner, Commander. Node 22 via
tsx. pnpm workspace member or standalone package.

OpenTUI requires Bun, but Ink does not, so this prototype targets Node/tsx as
the baseline that matches published-tool reality. As an optional extra bench
data point, also run it once with `bun run src/main.tsx` and record that
startup number next to the Node one.

**Code shape to expect:** React function components with hooks. A `useSkillctl`
hook holds state (rows, filter, staged set, selection); `App` renders
`<Box flexDirection="column">` with `<StatusBar/>`, `<FilterInput/>`, a mapped
list of `<Row/>`, and `<Footer/>`. `useInput` handles keybindings; the input
component handles typing. Applying is an async function in the hook with a
`phase: "idle" | "applying"` flag.

The CLI entry point is a small Commander program in `src/cli.ts`; the TUI entry
point in `src/main.tsx` imports the same fixture and hook. Rough sketch, about
200 to 260 lines for the TUI plus about 60 for the CLI:

```ts
// src/cli.ts
const program = new Command()
program.name("skillctl").description("prototype skill activation manager")
program.command("list").option("--json").action(printFixture)
program.command("enable").argument("<skills...>").action(wouldEnable)
program.command("tui").description("open the interactive manager").action(runTui)
program.parseAsync()
```

```tsx
// src/store.ts
function useSkillctl(rows: SkillRow[]) {
  const [state, setState] = useState(...)
  // filter, selection, staged: Set<string>, phase
  const filtered = useMemo(() => rows.filter(matchesFilter), [rows, filter])
  const stage = (id: string) => setState(s => ({...s, staged: toggle(s.staged, id)}))
  const apply = async () => { /* preview, await delay(300), flip states */ }
  return { state, filtered, stage, apply }
}

// src/main.tsx
function App() {
  const ctl = useSkillctl(fixture)
  useInput((input, key) => { /* j/k/space/r/q/? dispatch */ })
  return <Box flexDirection="column">{/* status, filter, rows, footer */}</Box>
}
```

**Known risks:** full-screen flicker on fast `j` repeats is Ink's historic
weak spot; watch for it during the held-`j` scenario. tsx cold start includes
TypeScript transpilation, so measure bench honestly (consider `tsx` with cache
warm, or precompile with esbuild for the bench run and note both numbers).

## Prototype B: OpenTUI + TypeScript

**Stack:** Bun 1.3+, `@opentui/core` + `@opentui/react`, Commander. Bun is
required by OpenTUI's native renderer; its runtime also starts faster than
Node, which will make the bench comparison interesting against Ink.

Commander runs fine under Bun, so the CLI here is nearly identical to
Prototype A's `src/cli.ts`, which makes the Commander comparison a constant
across both TS prototypes and isolates Cobra as the only CLI difference.

**Code shape to expect:** JSX that maps to OpenTUI primitives (`box`, `text`,
`input`) styled with flexbox props, closer to writing a native layout than
Ink's Yoga-based divs. Keyboard handling via `useKeyboard` from
`@opentui/react` or the `keymap` package. State is plain React state again,
so the hook from Prototype A ports almost unchanged; only the render tree and
input handling differ.

Rough sketch, similar line count:

```tsx
const { start } = await createCliRenderer(...)
start(() => (
  <box flexDirection="column" width="100%" height="100%">
    <StatusBar ... />
    <input onInput={setFilter} focused={filterFocused} ... />
    <box flexDirection="column" flexGrow={1}>
      {filtered.map(r => <Row key={r.id} row={r} ... />)}
    </box>
    <Footer />
  </box>
))
```

**Known risks:** the list is hand-rolled (OpenTUI core provides scroll boxes and
selects rather than a ready-made filterable table), so row virtualization at
`--rows 500` is on us; keep an eye on scroll behavior. API moves fast
(0.5.x), so pin exact versions. Mouse support exists if the prototype makes it
tempting: do not add it, note it.

## Prototype C: Go + Bubble Tea v2

**Stack:** Go 1.25+, `charm.land/bubbletea/v2`, `charm.land/bubbles/v2` (list or
table), `charm.land/lipgloss/v2`, Cobra for the CLI layer. This is the one
place where Cobra appears, which is the point: it is the reference standard for
Go CLI ergonomics and the direct comparison target for Commander.

The CLI is a Cobra command tree in `main.go` (or a small `cli.go`), with the
same command set as the TS prototypes; `skillctl tui` calls `tea.NewProgram`.

**Code shape to expect:** the Elm-architecture trio. A `model` struct holds
rows, filter, staged set, selection, phase; an `Update` method switches on
`tea.KeyPressMsg`; a `View` renders the same layout with lipgloss styles
declared once as package vars. Filter input comes from Bubbles `textinput`.

Rough sketch, about 250 to 300 lines:

```go
type model struct {
    rows     []Skill
    filtered []int
    filter   textinput.Model
    cursor   int
    staged   map[string]bool
    phase    phase // idle, preview, applying
}

func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    switch msg := msg.(type) {
    case tea.KeyPressMsg:
        switch msg.String() {
        case "j", "down": m.cursor++
        case "space": m.toggleStaged()
        case "enter": return m, m.apply()
        }
    case applyDoneMsg:
        m.flipStates()
    }
    return m, nil
}

func (m model) View() tea.View { return tea.NewView(m.render()) }
```

**Known risks:** the most code of the three and the most ceremony for simple
state changes, but the Bubbles table handles virtualization and scrolling for
free, which matters at `--rows 500`. Startup will likely win the bench
outright. Statically typed message types mean the compiler catches unhandled
phases; notice whether that feels helpful or noisy while writing it.

## Build order and timeboxing

1. **Fixture first** (30 min): write `skills.json` with 45 realistic entries
   (name, description, state, roots), including two-root skills and long
   descriptions for truncation testing.
2. **A: Ink** (half day): the familiar baseline. Get the spec implemented,
   run all five scenarios, record NOTES.md.
3. **B: OpenTUI** (half day): port the hook, rebuild the view. Bun required.
   Same scenarios, same notes.
4. **C: Go** (half day): Bubble Tea implementation. Same scenarios, same notes.
5. **Bench pass** (1 hour): `--bench` and `--rows 500` across all three, same
   terminal, same machine, five runs each. Include one Ink-on-Bun run as a
   bonus data point. Record in NOTES.md.
6. **CLI pass** (30 min): run the same five dummy commands in all three
   (`list`, `enable`, `doctor`, `list --json`, an unknown command). Compare
   help output, error messages, and exit codes side by side.
7. **Decision** (30 min): re-read NOTES.md, decide the stack for the real
   implementation, record the choice and reasoning at the top of NOTES.md.

Total: about two days. Prototypes are throwaway; copy nothing into the real
implementation except lessons and, if the TS path wins, the `useSkillctl` hook
shape.

## NOTES.md template

Fill one section per prototype immediately after using it, while impressions
are fresh:

- Startup (bench ms, and whether it feels slow in practice)
- Filter typing feel (does the list track keystrokes, any flicker)
- Scrolling at 45 and 500 rows (held-`j` repeat behavior, jank)
- Apply/refresh feel (spinner, state flip, any redraw artifacts)
- CLI ergonomics (help output quality, error messages, code needed for the same
  command set, Commander vs Cobra, completion story)
- Code impressions (lines, clarity, ceremony, where the complexity lives)
- Friction encountered while building (docs, API surprises, debugging)
- One-line verdict: "would I want to build the real tool in this?"
